All done. Four full agent sessions were run. The headline results:

1. **llama-bench throughput does not transfer to an agent session.** ~6 t/s
   generation and ~3 t/s prompt processing, against 10-13 and 71-78 measured by
   `llama-bench`. Prompt processing is the bottleneck and dominates wall clock.
2. **Context can go to 32768 for free.** The "full" 6 GiB card was never the
   ceiling — CUDA reports VMM and llama.cpp oversubscribes into system RAM.
3. **pi cannot use a 4096-token context at all** — a fixed safety margin makes
   every request return exactly one token, silently.
4. **Three of the four sampler values were llama.cpp's defaults, not Qwen's.**
   Now fixed for the whole roster.
5. **The model ships a real bug and declares it verified — four times out of
   four**, across two context sizes and two samplers.

Full detail: [`pi-small-qwen3-coder-findings-20260922.md`](pi-small-qwen3-coder-findings-20260922.md).

## The three traps, because each cost real time

**pi's 4096-token floor.** `clampMaxTokensToContext` subtracts a constant
`CONTEXT_SAFETY_TOKENS = 4096` and floors at `MIN_MAX_TOKENS = 1`. At
`contextWindow` 4096 every request returns one token with
`finish_reason: "length"`, and nothing errors — it reads as a broken model.
4096 is exactly the number `llama-bench` validates at, so it is the natural
value to reach for. `ctxUsabilityWarning()` in `lib/roster.ts` now warns; the
default ladder stops at 8192.

**A full VRAM reading is not a context ceiling.** `nvidia-smi` pins at 6037 MiB
of 6144 at ctx 8192, 16384 *and* 32768 — identical, because it is reporting the
oversubscription ceiling. Do not tune context down on the strength of that
number. Also: do **not** quantize the KV cache here (`q8_0` saves nothing and
costs ~25% generation speed), and `-fa` is already on by default.

**Engine defaults masquerade as chosen config.** The roster's `top_p 0.95` /
`top_k 40` were llama.cpp's defaults, and `repeat_penalty`/`min_p` were never
passed. Assert sampler values against the actual argv or request body — several
coincide with engine defaults, so reading the config proves nothing. Wiring the
fix immediately produced a second instance: `serve.mjs` built its sampler
object without the new fields and sent `String(undefined)`.

## Gotchas for whoever picks this up

- **Leftover stub servers.** Every server `serve.mjs` starts is detached by
  design, so a test run killed partway through leaves one holding the port. The
  next run then *adopts* it and fails somewhere unrelated. Both test files now
  preflight and say exactly what to kill. This bit me three times.
- **`$!` in MSYS bash is not a Windows PID.** `taskkill //PID $!` fails and a
  following `wait` hangs forever. Use `kill` for a process the shell started;
  `taskkill` only for a PID that came from Node (`child.pid`).
- **Long runs need `schtasks`.** A raw `ssh` command that outruns its timeout is
  torn down and takes the run with it — already in `CLAUDE.md`, and still true.
- **Apertus's card is gated** (HTTP 401), so it is the one model still on roster
  default sampling. Recorded in its `notes`; re-check if access appears.
- `coding-bench/models.conf` deliberately serves every model identically for
  comparability. It shares no config with `roster.json` — changing one does not
  affect the other. Keep it that way.

## Open threads

- **The `--n-cpu-moe 34` sweep optimised `pp512`**, which this session shows is
  the wrong target for agent use: agent turns are small batches that lose the
  amortisation `pp512` is built to capture. A sweep against *incremental-turn*
  throughput would likely pick a different number.
- Would `-b`/`-ub` tuning help the small-batch case, or is the per-batch expert
  streaming cost irreducible?
- **Qwen3.6-35B-A3B has never been run through pi-small.** Its llama-bench
  numbers are close enough that it probably behaves the same, but that is an
  assumption.
- The swapped-variable bug survived context and sampler changes. If it is worth
  chasing, the next lever is the system prompt — pi-small serves a near-empty
  one by design, and this model may simply need to be told to check its output
  against the spec. `roster.json` `systemPrompt` is per-model and exists for
  exactly that.
- Whether the roster's now-correct samplers change the small models' behaviour
  is **untested** — LFM2.5 especially, which drops 0.7 → 0.1 and is the model
  that overwrote task files twice.
