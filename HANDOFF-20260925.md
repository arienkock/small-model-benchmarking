## Where things stand

- **Architecture (verified on the laptop).** `workflow/run.ts` is the host
  side: it starts `proxy.mjs` (llama-server behind it on backend port 8125),
  runs one pi-small process in the Docker sandbox, and sends one
  `/workflow run` or `/workflow review` command. The workflow runs inside the
  plugin (`lib/workflow-command.ts`). Model switches go through the proxy;
  pi never restarts. What was verified:
  - the Docker e2e passes, grader 28/28;
  - a real run with Granite switched to Spark in 8 s within the same process;
  - the best-attempt snapshots, and resume after an interruption;
  - at the end of a run, run.ts stops the proxy and its llama-server.
- **Best result so far.** The overnight rotation (Granite → Spark → LFM →
  MiniCPM, 10 turns / 15 min per session) finished T1 and T2 of books-api:
  grader 24/28 (re-graded with the fairer grader: 24/28, 0 skipped). The four
  real defects in that workspace (`workflow-runs/overnight-5/ws`):
  1. a non-integer id in the path returns 404 instead of 400 (the shared
     plan's scenario S7 wrongly says 404);
  2. the `q` filter looks up a field that does not exist, so it crashes;
  3. create with a missing title crashes on `None` (no 400);
  4. create with a wrong-typed title crashes the same way.

  Secondary: a non-numeric `id=` filter crashes, and the "missing required
  field" branch can never be reached.
- **Config in use** (`workflow/configs/rotation-minimal.json`):
  - `feedback: "failures"` (verdict plus one line per failing test);
  - `retryWorkspace: "best"`;
  - `codingTools: ["bash", "edit"]`;
  - `maxTurns: 10`;
  - the four-model rotation.
- **books-api task.json** has a precise server convention: `make_server(port)`;
  tests run it on port 0 in a daemon thread.
- **Judging fixes applied.**
  - The grader reports checks whose fixture data is missing as skipped, not
    failed, and compares books by their own fields.
  - The harness test count is one per scenario; integration steps no longer
    add +1.

## Review experiment (in progress)

Goal: find the review prompt and model combination that best finds defects,
review only, no fixing. The prompts are `lib/review.ts` `REVIEW_VARIANTS`:
completeness, correctness, fidelity, and all three combined. Each asks for
prioritised findings through the `submit_findings` tool.

Run `workflow-runs/review-1` (the overnight-5 workspace, all 16 sessions,
results in `reviews.json`):

| model | completeness | correctness | fidelity | all |
|---|---|---|---|---|
| Granite | 5 findings | 4 | 2 | 3 (always submits in 2 turns, under 3 min) |
| Spark | none | none | none | none (turn or time limit every time) |
| LFM | 0 | 2 | 0 | 0 |
| MiniCPM | none | none | none | none (turn limit twice; twice one response filled the output cap without a tool call) |

- **Not done yet:** scoring the submitted findings against the four known
  defects above.
- **What `tools/session-summary.py` showed for Spark:** it was probing real
  defects correctly (wrong-type title, `id=abc`), one ~90 s turn per probe, and
  ran out of turns before submitting.
- **Being built in another session:**

    so far");
  - a continuation session that carries those findings forward;
  - a review-specific compaction prompt (`session_before_compact` → cancel →
    `ctx.compact({customInstructions})`).

## Laptop procedures learned the hard way

- Check `coding-bench/.bench-lock/info` before using the GPU.
- Long jobs go under `schtasks`, never `nohup`.
- **Stopping a run:**
  1. `schtasks //end`;
  2. `docker kill` the `wf-*` containers;
  3. kill any leftover `llama-server.exe` (`workflow-overnight-stop.sh`, or
     `taskkill //IM llama-server.exe //F`);
  4. check with `netstat -ano | grep ":8123 .*LISTENING"`.

  A killed run can leave an untracked llama-server behind, and on Windows two
  servers can both listen on the same port. `serve.mjs` now refuses when the
  port answers as a different model.
- **Deploying:** `git archive HEAD pi-small | ssh benchlaptop 'cd /d/llama.cpp && tar xf -'`,
  run from the repo root. The laptop checkout is `master` with these files on
  top. Backups: `pi-small/.bak-pre-proxy-*.tar.gz` and `pi-small/.bak-pre-replay/`.
- Run `tools/session-summary.py` on the laptop, where the runs are:
  `python tools/session-summary.py workflow-runs/<run>/steps/<step>`.
- Run directories: `/d/llama.cpp/pi-small/workflow-runs/`. Each holds
  `workflow.log`, `events.jsonl`, `steps/`, `snapshots/`, `home/` (the agent's
  pi home) and `ws/`.
